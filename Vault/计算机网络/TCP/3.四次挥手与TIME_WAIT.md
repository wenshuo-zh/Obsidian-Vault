# TCP 四次挥手与 TIME_WAIT

## 一、本次学习目标

- 理解 TCP 为什么关闭连接通常需要四次挥手；
- 能按顺序说明 `FIN`、`ACK` 各自表示什么；
- 区分主动关闭方与被动关闭方的状态变化；
- 解释 `TIME_WAIT` 的作用，并区分它和 `CLOSE_WAIT`。

本次只学习正常关闭流程，不展开同时关闭、复位报文和 `SO_LINGER` 等特殊情况。

## 二、先建立直觉：两个方向分别关闭



TCP 是全双工的：连接建立后，A 可以向 B 发送数据，B 也可以同时向 A 发送数据。A 说“我这边没有数据要发了”，不代表 B 也已经发完。因此，TCP 需要分别关闭两个方向：

- `FIN`：发送方表示自己不会再发送新数据；
- `ACK`：接收方确认已经收到对方的关闭请求。

收到 A 的 `FIN` 后，B 仍可以把尚未发送完的数据发给 A。等 B 也准备好关闭自己的发送方向时，才发送自己的 `FIN`。

## 三、四次挥手的过程

假设 A 主动关闭，B 被动关闭：

```text
A                                      B
| -------- FIN ----------------------> |
| <------- ACK ----------------------- |
|         B 仍可继续发送数据            |
| <------- FIN ----------------------- |
| -------- ACK ----------------------> |
```

1. A 发送 `FIN`：A 不再发送数据，进入 `FIN_WAIT_1`。
2. B 回复 `ACK`：确认收到 A 的 `FIN`。A 收到确认后进入 `FIN_WAIT_2`；B 进入 `CLOSE_WAIT`，但仍可继续发送数据。
3. B 的数据发送完毕后发送 `FIN`，进入 `LAST_ACK`。
4. A 回复 `ACK`，进入 `TIME_WAIT`；B 收到确认后进入 `CLOSED`。A 等待一段时间后也进入 `CLOSED`。

通常称为“四次挥手”，因为两个方向的关闭需要分别确认。若 B 很快就准备好关闭，第二个 `ACK` 和 B 的 `FIN` 有时可以放在同一个 TCP 报文中；四步是便于理解的常见流程，不代表抓包一定总有四个分开的报文。

## 四、双方状态变化

| 角色      | 常见状态顺序                                                               |
| ------- | -------------------------------------------------------------------- |
| 主动关闭方 A | `ESTABLISHED` → `FIN_WAIT_1` → `FIN_WAIT_2` → `TIME_WAIT` → `CLOSED` |
| 被动关闭方 B | `ESTABLISHED` → `CLOSE_WAIT` → `LAST_ACK` → `CLOSED`                 |

主动关闭方不一定是客户端；谁先发起关闭，谁就是主动关闭方。正常业务里谁调用关闭、谁先结束数据发送，都会影响哪一端进入 `TIME_WAIT`。

## 五、为什么需要 TIME_WAIT

主动关闭方发送最后一个 `ACK` 后不会马上销毁连接，而是进入 `TIME_WAIT`，通常等待一段 `2MSL` 时间。MSL 是报文在网络中可能存活的最长时间；具体等待时长由系统实现和配置决定，不必在入门阶段死记固定秒数。

等待主要有两个作用：

1. 如果最后的 `ACK` 丢失，对端会重传 `FIN`；主动关闭方仍能用该连接状态再次回复 `ACK`。
2. 等旧连接的延迟报文从网络中消失，减少它们干扰之后复用相同连接四元组的风险。

因此，看到少量短暂的 `TIME_WAIT` 通常是正常现象。大量 `TIME_WAIT` 可能说明短连接创建频繁，需要结合连接数、端口资源和业务连接复用策略一起分析；不能仅凭这个状态就认定 TCP 出错。

## 六、后端排查常见状态

- **`CLOSE_WAIT`**：本机已经收到对端的 `FIN`，但本机应用还没有关闭对应 socket。少量短暂出现正常；如果持续大量堆积，优先检查程序是否漏掉关闭连接、处理流程是否卡住。
- **`TIME_WAIT`**：本机完成主动关闭后，内核暂时保留连接状态。它一般会自行消失，不表示应用还持有打开的 socket。

在常见正常关闭路径中，应用关闭连接 socket 后，由内核继续完成 TCP 挥手；`close()` 是本地系统调用，不是直接发送给对端的一条 TCP 报文。

## 七、Linux tcpdump + Windows Wireshark 观察实验

推荐采用“虚拟机捕获、Windows 分析”的分工：Ubuntu 虚拟机中的 `tcpdump` 直接监听产生流量的 Linux 网卡并保存原始报文；Windows 中的 Wireshark 打开 `.pcap` 文件，负责图形化解析。Windows Wireshark 不必直接捕获虚拟机流量，因为 VMware 的 NAT、桥接或仅主机模式可能让宿主机看不到完整的客户机报文。

### 1. 先观察内核状态

```bash
ss -tan state time-wait
ss -tan state close-wait
```

远程 HTTPS 连接的 `TIME_WAIT` 可能在服务端而非本机；本次抓包正是服务端先发 FIN，因此只在 Ubuntu 客户端查 `TIME_WAIT` 不一定能看到该连接。下面用本机短连接稳定观察两种状态，不需要安装额外软件。

终端一启动一个延迟关闭的本地 TCP 服务端：

```bash
python3 -c 'import socket,time; s=socket.socket(); s.setsockopt(socket.SOL_SOCKET,socket.SO_REUSEADDR,1); s.bind(("127.0.0.1",9000)); s.listen(1); c,_=s.accept(); print("accepted; server will close in 6 seconds", flush=True); time.sleep(6); c.close(); s.close()'
```

终端二连接后立即关闭客户端 socket：

```bash
python3 -c 'import socket; s=socket.create_connection(("127.0.0.1",9000)); s.close(); print("client closed first")'
ss -tnp state close-wait
sleep 7
ss -tan state time-wait
```

预期先在 `CLOSE_WAIT` 输出中看到服务端本地端口 `9000`，因为服务端收到了客户端 FIN、但应用还在等待；服务端 6 秒后关闭连接，客户端作为主动关闭方进入 `TIME_WAIT`，随后可在第二条 `ss` 输出中看到它。若手动操作太慢而错过 `CLOSE_WAIT`，重新运行服务端与客户端即可。

本机实测中，`ss -tnp state close-wait` 输出过服务端 `127.0.0.1:9000`、对端 `127.0.0.1:44882`，以及仍持有连接的 `python3` 进程；另一次重新运行时，新截图显示对端临时端口为 `39864`。两次输出都说明客户端先发送了 FIN，服务端收到了关闭请求但应用尚未调用 `close()`，所以服务端处于 `CLOSE_WAIT`。另一次 `TIME_WAIT` 截图显示客户端本地端口 `44882`、对端端口 `9000`；临时端口会随每次运行变化，因此不要把不同运行的端口输出当成同一条连接。

### 2. 用 tcpdump 保存完整 TCP 会话

不要只过滤 FIN；先把本次 443 连接的完整报文保存下来，方便在 Wireshark 中同时查看三次握手、数据传输和四次挥手。

终端一（Ubuntu 虚拟机）执行：

```bash
sudo tcpdump -i any -nn -s 0 -Z "$(id -un)" -w tcp-close.pcap 'tcp port 443'
```

参数含义：

- `-i any`：监听所有网卡，适合 Ubuntu 虚拟机；
- `-nn`：不做 DNS 和端口名解析，输出更稳定；
- `-s 0`：保存完整报文，不截断 TCP 负载；
- `-Z "$(id -un)"`：打开抓包接口后降权为当前用户，避免 pcap 文件只能由 root 读取；
- `-w tcp-close.pcap`：保存为 Wireshark 可打开的 pcap 文件。

终端二（Ubuntu 虚拟机）建立一次明确要求关闭连接的 HTTPS 请求：

```bash
curl --http1.1 -v --max-time 15 \
  -H 'Connection: close' \
  https://example.com/
```

请求完成后回到终端一按 `Ctrl+C` 停止抓包。可以先在 Ubuntu 中用 tcpdump 文本方式检查 FIN：

```bash
tcpdump -nn -r tcp-close.pcap 'tcp[tcpflags] & tcp-fin != 0'
```

### 3. 将 pcap 传到 Windows

先在 Ubuntu 虚拟机查看网卡地址：

```bash
hostname -I
```

确认 Windows 宿主机能够访问虚拟机的 IP。然后在 Windows PowerShell 执行：

```powershell
scp ubuntu用户名@虚拟机IP:~/tcp-close.pcap .
```

把示例中的 `ubuntu用户名`、`虚拟机IP` 替换成实际值；命令末尾的 `.` 表示保存到 PowerShell 当前目录。Windows 未安装 OpenSSH Client 时，可以通过 VMware 共享文件夹、VSCode Remote-SSH 文件管理或其他已配置的文件传输方式复制。不要重新用 Windows 网卡抓包来替代 Ubuntu 中的捕获。

### 4. 用 Windows Wireshark 分析 pcap

在 Windows Wireshark 中打开复制过来的 `tcp-close.pcap` 文件。本实验不要求在 Ubuntu 虚拟机中安装或运行 Wireshark 图形界面。

Wireshark 显示过滤器建议按顺序使用：

```text
tcp.flags.syn == 1 || tcp.flags.fin == 1 || tcp.flags.reset == 1
```

先找到本次连接的 SYN 报文，右键选择 **Follow → TCP Stream**，记下该连接的编号，然后用更精确的过滤器：

```text
tcp.stream eq N
```

把 `N` 替换为实际编号。随后观察：

1. `SYN`、`SYN, ACK`、最终 `ACK`；
2. 主动关闭方先发送的 `FIN, ACK`；
3. 对端的 `ACK`，以及之后对端发送的 `FIN, ACK`；
4. 主动关闭方最后的 `ACK`；
5. 每个报文的 Source、Destination、Sequence Number、Acknowledgment Number。

若第二次挥手中的 `ACK` 与被动方的 `FIN` 合并，抓包中可能只有三个关闭相关报文，这是正常的。Wireshark 的 **Time**、**Source/Destination** 和 **Info** 列可以帮助判断方向；不要只按报文数量判断协议是否正确。

### 5. 实验结果与 `ss` 对照

抓包结束后再次执行：

```bash
ss -tan state time-wait
ss -tan state close-wait
```

如果 `TIME_WAIT` 很快消失，优先以 pcap 中的 FIN/ACK 顺序为准；`ss` 是瞬时状态观察，不能证明过去没有发生过挥手。实验无法联网、没有 `sudo` 或没有图形界面时，仍可完成 tcpdump 保存和命令行分析，不要为了抓包修改防火墙规则。

## 八、四次挥手报文丢失与超时重传

以下假设 A 主动关闭、B 被动关闭，讨论一次只丢失一个报文的常见情况。发送 `FIN` 后，发送方会等待确认；超时后可能重传。实际重试次数和等待时间由 TCP 实现、系统配置和 socket 状态影响，不要求背固定数值。

### 1. 第一次报文：A 的 FIN 丢失

- A 已发送 `FIN`，停留在 `FIN_WAIT_1` 等待确认；
- B 没收到 `FIN`，仍认为连接处于 `ESTABLISHED`，也不知道 A 已准备关闭；
- A 超时后重传 `FIN`；若始终得不到响应，系统最终会放弃该连接。

### 2. 第二次报文：B 对 A 的 FIN 的 ACK 丢失

- B 收到 A 的 `FIN` 后发送 `ACK`，进入 `CLOSE_WAIT`；
- ACK 丢失后，A 仍停留在 `FIN_WAIT_1`，超时后可能重传 `FIN`；
- B 收到重复的 `FIN` 后再次回复 `ACK`，B 不会因此重新创建连接；
- A 收到 ACK 后进入 `FIN_WAIT_2`。B 仍可在 `CLOSE_WAIT` 中发送尚未完成的数据。

### 3. 第三次报文：B 的 FIN 丢失

- B 发送 `FIN` 后进入 `LAST_ACK`，等待 A 的确认；
- A 仍处于 `FIN_WAIT_2`，等待 B 关闭发送方向；
- B 超时后重传 `FIN`；A 收到后回复 ACK，并进入 `TIME_WAIT`；B 收到 ACK 后进入 `CLOSED`；
- Linux 的 `tcp_fin_timeout` 可能限制**已孤儿化的 `FIN_WAIT_2` socket**停留时间；它不是所有 TCP 实现都固定等待的“FIN 超时”，具体值取决于内核配置和 socket 是否仍由应用持有。

### 4. 第四次报文：A 的最后一个 ACK 丢失

- A 收到 B 的 `FIN` 并回复最后一个 `ACK` 后进入 `TIME_WAIT`；
- ACK 丢失时，B 留在 `LAST_ACK`，超时后重传 `FIN`；
- A 在 `TIME_WAIT` 收到重复的 `FIN` 后再次回复 `ACK`，并重新等待 `2MSL`；
- B 收到 ACK 后进入 `CLOSED`，A 的 `2MSL` 等待结束后也进入 `CLOSED`。

Linux 的 `tcp_orphan_retries` 等参数会影响部分已孤儿化 socket 的重试行为；这些是 Linux 实现细节，不是 TCP 协议规定的固定次数。排查时不要仅凭默认值推断连接一定在某个精确秒数关闭。

## 九、本次手写笔记与 Wireshark 截图复盘

手写流程与标准状态机整体一致，复盘时要抓住以下对应关系：

| 报文 | 方向 | 关键状态变化 |
| --- | --- | --- |
| A 的 `FIN` | A → B | A：`ESTABLISHED` → `FIN_WAIT_1` |
| B 的 `ACK` | B → A | B：`ESTABLISHED` → `CLOSE_WAIT`；A 收到确认后进入 `FIN_WAIT_2` |
| B 的 `FIN` | B → A | B：`CLOSE_WAIT` → `LAST_ACK`；A 收到 FIN 并回复 ACK 后进入 `TIME_WAIT` |
| A 的最后 `ACK` | A → B | B 收到后：`LAST_ACK` → `CLOSED`；A 等待 `2MSL` 后关闭 |

收到 FIN 后，确认号通常为该 FIN 的序列号加 1，因为 FIN 会占用一个序列号；若该报文还携带数据，则确认号还要计入数据字节数。主动关闭方发送 FIN 后不能再发送新的应用数据，但仍可以接收对端数据。

本次完整 Wireshark Stream 共 17 个报文。此前使用的过滤器 `tcp.flags.syn == 1 || tcp.flags.fin == 1 || tcp.flags.reset == 1` 只留下 4 个匹配项，会隐藏纯 ACK；改用 `tcp.stream eq 0` 后可以看到整个连接的握手、TLS 数据和关闭过程。

### 1. 从抓包还原本次关闭顺序

连接四元组为客户端 `192.168.52.129:52788` 与服务端 `172.66.147.243:443`。前 3 个报文完成三次握手。关闭过程如下：

| 包号 | 方向与标志 | 相对序列号/确认号 | 观察与状态推断 |
| --- | --- | --- | --- |
| 12 | 服务端 → 客户端，`FIN, PSH, ACK` | `Seq=3997, Ack=714`，TCP 数据长度 1478；下一序列号为 5476 | 服务端在携带 TLS 数据时同时发 `FIN`，进入 `FIN_WAIT_1`；FIN 和数据各自占用序列空间 |
| 13 | 客户端 → 服务端，`ACK` | `Seq=714, Ack=5476` | 确认服务端数据和 FIN；客户端进入 `CLOSE_WAIT`，服务端收到该 ACK 后进入 `FIN_WAIT_2` |
| 14 | 客户端 → 服务端，TLSv1.3 Application Data | 截图显示 TLS 应用数据 | 对端发送 FIN 后仍可接收数据；客户端也仍可在自己的发送方向发送数据 |
| 15 | 服务端 → 客户端，`ACK` | `Seq=5476, Ack=738` | 确认客户端此前发送的数据；服务端仍等待客户端关闭发送方向 |
| 16 | 客户端 → 服务端，`FIN, ACK` | `Seq=738, Ack=5476` | 客户端发送 FIN，进入 `LAST_ACK` |
| 17 | 服务端 → 客户端，`ACK` | `Seq=5476, Ack=739` | 确认客户端 FIN；客户端收到后进入 `CLOSED`，服务端进入 `TIME_WAIT`，等待 `2MSL` 后关闭 |

因此，这次实际 TCP 挥手顺序是：

```text
服务端 FIN,ACK (#12)
→ 客户端 ACK (#13)
→ 客户端仍发送 TLS 数据 (#14)，服务端确认 (#15)
→ 客户端 FIN,ACK (#16)
→ 服务端 ACK (#17)
```

**本次先发送 FIN 的是服务端，不是发起 curl 请求的客户端。** `Connection: close` 请求服务器在响应后关闭连接；抓包中服务端先发 FIN，因此按正常状态机服务端是主动关闭方并进入 `TIME_WAIT`，客户端是被动关闭方，经历 `CLOSE_WAIT`、`LAST_ACK` 后关闭。`ss` 状态没有在这次抓包中同步采样，所以这些状态是根据 TCP 报文顺序推断，而非直接从 `ss` 输出观测到。

Wireshark 显示的相对确认号也能验证 FIN 占用一个序列号：第 12 号包数据长度为 1478，`3997 + 1478 + 1 = 5476`，对应第 13 号包的 `Ack=5476`；第 16 号包的 `Seq=738`，所以服务端最后确认 `Ack=739`。

## 十一、学习记录

- 已完成首次口头复述：TCP 是双向数据传输，两个方向需要分别关闭；收到对端 `FIN` 后，本机仍可发送剩余数据；主动关闭方发送最后 `ACK` 后进入 `TIME_WAIT`。
- 订正：收到对端 `FIN` 的一方进入 `CLOSE_WAIT`；应用发送本方 `FIN` 后进入 `LAST_ACK`；`TIME_WAIT` 通常等待 `2MSL` 后进入 `CLOSED`。四次挥手是常见流程，`ACK` 与 `FIN` 可能合并。
- 已根据手写笔记梳理四次挥手四个报文的方向、序列号确认关系与双方状态变化，并补充四种报文丢失后的重传过程。
- 已完成 Ubuntu `tcpdump` 捕获并在 Windows Wireshark 打开 pcap；使用 `tcp.stream eq 0` 查看了完整的 17 个报文。
- 已确认服务端第 12 号包为 `FIN, PSH, ACK`，客户端第 13 号包 ACK 确认；客户端仍发送 TLS 数据后，于第 16 号包发送 `FIN, ACK`；服务端第 17 号包最终 ACK 确认。
- 已根据相对序列号验证 FIN 占用一个序列号：服务端 `3997 + 1478 字节数据 + 1(FIN) = 5476`，客户端最后的 FIN 则由服务端以 `Ack=739` 确认。
- 本次服务端先发 FIN，是主动关闭方；按状态机服务端进入 `TIME_WAIT`，客户端经过 `CLOSE_WAIT`、`LAST_ACK` 后关闭。此处状态由抓包推断，尚未用 `ss` 同步观察。
- 已完成本机延迟关闭实验：`ss -tnp state close-wait` 观察到服务端 `127.0.0.1:9000` 对端为临时端口 `44882`，另一次重新运行时对端为 `39864`；两次都确认服务端收到客户端 FIN 后暂处于 `CLOSE_WAIT`。另一次 `ss` 输出显示客户端本地端口 `44882`、对端端口 `9000` 处于 `TIME_WAIT`。
- 本次复述已掌握状态迁移：主动关闭方发送最后一个 `ACK` 后进入 `TIME_WAIT`；通常等待 `2MSL` 后进入 `CLOSED`。本机收到对端 `FIN` 后进入 `CLOSE_WAIT`，应用调用 `close()`、发送本方 `FIN` 后进入 `LAST_ACK`，等待对方确认后关闭。
- 术语订正：`MSL` 是报文在网络中允许存活的最长时间，`TIME_WAIT` 等待的是 `2MSL`；`CLOSE_WAIT` 的主体是收到 FIN 的本机，而不是“对端接受到 FIN”。
- 待补充口头复述：`TIME_WAIT` 的两个作用，以及大量 `CLOSE_WAIT` 时应优先排查应用是否没有及时关闭 socket 或处理流程是否卡住。
