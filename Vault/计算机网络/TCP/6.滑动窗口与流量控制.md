# TCP 滑动窗口与流量控制

## 一、本次学习目标

- 理解停止等待为什么效率低；
- 理解滑动窗口允许多个报文段在未收到 ACK 前连续发送；
- 区分接收窗口 `rwnd` 与拥塞窗口 `cwnd`；
- 看懂 TCP 首部的通告窗口和握手中的窗口扩大选项；
- 用 tcpdump + Wireshark 观察 SYN、SYN+ACK 的 MSS、Window Scale、SACK Permitted。

本节先学习流量控制和窗口基本模型，不深入慢启动、拥塞避免、快速恢复，也不人为制造丢包。

## 二、为什么需要窗口

如果发送方每发一个报文就停下来等待 ACK，通信过程会变成：

```text
发送一个报文 -> 等待往返时间 RTT -> 收到 ACK -> 再发下一个
```

当网络 RTT 较大时，发送方大部分时间在等待，链路带宽没有被充分利用。滑动窗口允许发送方一次发送多个尚未确认的字节，让网络中同时存在多个报文段。

窗口不是“只能发送固定数量的报文”，而是发送方当前允许保持在途、尚未被确认的字节范围。窗口会随着 ACK 到达而向前滑动。

## 三、简化模型

假设发送窗口大小为 300 字节，发送方从 `Seq=1000` 开始：

```text
已确认       在途、允许发送                 暂时不能发送
1000~1099    1100~1299（窗口内）            1300 以后
```

当接收方回复 `Ack=1100`：

- `1000~1099` 已被累计确认；
- 左边界从 1000 移到 1100；
- 如果窗口大小仍为 300，右边界也向前移动 100 字节；
- 发送方可以继续发送新的 `1300~1399` 数据。

这就是“滑动”：已确认的数据离开窗口，新的数据进入窗口。

## 四、流量控制：保护接收方

接收方应用读取数据的速度可能比发送方发送速度慢。如果发送方无限制发送，接收方内核接收缓存可能被填满。TCP 通过接收方在 ACK 中通告的**接收窗口 `rwnd`**告诉发送方：

> 我当前还可以接收这么多字节，请不要超过这个范围发送未确认数据。

接收方应用读取缓存后，空闲空间增加，后续 ACK 中的通告窗口可能变大；缓存接近满时，通告窗口可能变小。

### 零窗口

如果接收方通告窗口为 0，发送方暂时不能继续发送新的数据。TCP 通常会通过窗口探测机制周期性确认接收方是否重新打开窗口。零窗口是接收能力暂时不足，不等同于连接已经关闭。

## 五、接收窗口与拥塞窗口

发送方实际能发送的数据量通常同时受两个限制：

```text
实际发送上限 = min(rwnd, cwnd)
```

- `rwnd`（receive window）：接收方根据自身缓存能力通告，解决**流量控制**；
- `cwnd`（congestion window）：发送方根据网络拥塞情况维护，解决**拥塞控制**。

本节重点是 `rwnd`。`cwnd` 只先知道名字和作用，慢启动、拥塞避免等后续学习。

## 六、握手中的窗口和 TCP 选项

### 1. Window

SYN 或普通 TCP 报文中的 `Window` 是发送方当前通告的接收窗口值。它表示对方最多可以发送多少未确认数据，但实际可发送范围还会受到拥塞窗口等因素限制。

### 2. Window Scale

早期 TCP 窗口字段只有 16 位，最大表示 65535 字节。高速或高延迟网络需要更大的接收窗口，因此双方可在 SYN/SYN+ACK 中协商 `Window Scale`。之后实际窗口大致为：

```text
实际接收窗口 = 报文 Window 字段 × 2^Window Scale
```

窗口扩大选项只在握手中协商；后续报文使用协商出的比例解释 Window 字段。抓包时要同时记录原始 Window 和 Scale，不能只看其中一个。

### 3. MSS

`MSS（Maximum Segment Size）` 表示本端愿意接收的单个 TCP 数据段最大负载长度，不包括 TCP/IP 首部。它通常在 SYN 中携带，常见以太网 IPv4 场景可能看到 1460，但实际值取决于路径 MTU 和配置。

### 4. SACK Permitted

SYN 中的 `SACK Permitted` 表示本端支持选择确认。它只是能力协商；真正发生乱序或丢包时，后续报文才可能携带 SACK 区块。不要把握手中的 `SACK Permitted` 误认为已经发生了 SACK 重传。

## 七、抓包实验

### Ubuntu 终端一：启动本地服务

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

### Ubuntu 终端二：开始保存完整流量

```bash
sudo tcpdump -i lo -nn -s 0 -w tcp-window-20261015.pcap 'tcp port 8000'
```

参数含义：监听回环接口，数字显示，保存完整报文，写入 pcap，只捕获 8000 端口。

### Ubuntu 终端三：建立连接

```bash
curl --http1.1 -v --max-time 5 http://127.0.0.1:8000/
```

请求完成后回到终端二按 `Ctrl+C`，再读取：

```bash
tcpdump -nn -r tcp-window-20261015.pcap
```

### Windows Wireshark 观察顺序

1. 打开 pcap，使用 `tcp.port == 8000`；
2. 找到客户端 SYN 和服务端 SYN+ACK；
3. 展开 TCP 首部，记录两条报文的 `Window`、`MSS`、`Window Scale`、`SACK Permitted`；
4. 找到第三次握手 ACK，确认它确认了服务端 SYN；
5. 用 **Follow -> TCP Stream** 确定流编号，再使用 `tcp.stream eq N`；
6. 对比后续数据报文的 `Window`，理解通告窗口会随接收缓存变化。

建议记录：

| 报文 | 方向 | 标志 | Window | MSS | Window Scale | SACK Permitted |
| --- | --- | --- | --- | --- | --- | --- |
| SYN | 客户端 → 服务端 | SYN | 待抓包 | 待抓包 | 待抓包 | 待抓包 |
| SYN+ACK | 服务端 → 客户端 | SYN, ACK | 待抓包 | 待抓包 | 待抓包 | 待抓包 |
| ACK | 客户端 → 服务端 | ACK | 待抓包 | 通常无 | 通常无 | 通常无 |

## 八、易错点

- 滑动窗口不是“只能发送一个固定数量的报文”，核心是允许一定范围的未确认字节在途；
- `rwnd` 是接收方能力，`cwnd` 是网络拥塞估计，二者不能混为一谈；
- Window 字段是通告值，不等于本机此刻真实已经使用的缓存大小；
- Window Scale 只在 SYN/SYN+ACK 中协商，不能只看后续 Window 原始数字；
- MSS 是 TCP 数据负载上限，不包含 IP 和 TCP 首部；
- `SACK Permitted` 表示支持 SACK，不表示抓包中一定已经发生丢包或 SACK。
