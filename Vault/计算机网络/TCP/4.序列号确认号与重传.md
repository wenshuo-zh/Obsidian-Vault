# TCP 序列号、确认号与数据报文重传

## 一、本次学习目标

- 理解 TCP 是可靠、有序的**字节流**；
- 看懂 TCP 报文中的序列号 `Seq` 与确认号 `Ack`；
- 理解累计确认、超时重传和快速重传的基本逻辑；
- 能在 Wireshark 中观察一条 TCP 流的序列号与确认号。

本节不学习滑动窗口、拥塞控制、拆包粘包和 SACK 的具体实现，这些后续单独学习。

## 二、它解决什么问题

IP 网络只能尽力交付报文：报文可能丢失、乱序、重复或延迟。TCP 用序列号标记字节位置，用确认号告知已连续收到的位置；发送方根据确认情况重传缺失的数据，从而向应用提供有序、可靠的字节流。

TCP 不保留“第几个 `send()`”的边界。应用写入的数据会被 TCP 按合适大小拆分成若干报文段；接收方读数据时也可能一次读到部分或多个发送结果。

## 三、序列号：给字节编号

`Seq` 表示**本报文段数据部分第一个字节的编号**，不是“第几个报文”。

```text
发送方发送 100 字节数据：Seq = 5000，Len = 100

本段覆盖的字节序列号：5000 ~ 5099
下一段新数据的 Seq：5100
```

建立连接时，双方各自选择初始序列号（ISN）。后续使用相对序列号理解抓包即可；Wireshark 默认通常展示相对值，便于观察。

`SYN` 和 `FIN` 虽然一般不携带应用数据，但各占用一个序列号。因此握手或挥手后的确认号通常会加 1。

### 首部中的序列号相关字段

- **初始序列号（ISN）**：连接建立时双方分别选择的起始序列号，通常不可简单预测；
- **普通数据段**：下一段新数据的 `Seq = 本段 Seq + 数据长度`；
- **SYN/FIN**：各自占用一个序列号，即使数据长度为 0，也会让后续确认号前进 1；
- **普通 ACK**：确认报文本身通常不携带数据，也不占用新的序列号。

## 四、确认号：我下一步想收到什么

`Ack` 表示：**截至 `Ack - 1` 的所有字节已经按序连续收到，现在期望下一个字节是 `Ack`。**

例如接收方发送：

```text
Ack = 5100
```

表示 `5000 ~ 5099` 已连续收到，接下来希望收到 `Seq = 5100` 的数据。它不是“已经收到了 5100 个字节”，也不一定是“收到了第 5100 个字节”。

## 五、累计确认与乱序到达

假设发送方依次发送：

```text
报文段 A：Seq = 100，Len = 100  -> 覆盖 100 ~ 199
报文段 B：Seq = 200，Len = 100  -> 覆盖 200 ~ 299
报文段 C：Seq = 300，Len = 100  -> 覆盖 300 ~ 399
```

若 B 丢失、C 先到达，接收方缺少 `200 ~ 299`，就不能向应用交付一段连续的 `100 ~ 399` 字节流。因此它仍会回复：

```text
Ack = 200
```

这叫**累计确认**：确认号只推进到连续数据的末尾。接收方是否暂存 C、是否额外携带乱序块信息，属于具体 TCP 实现和后续 SACK 话题；入门阶段先记住“缺中间数据时，Ack 不越过缺口”。

## 六、数据丢失后如何重传

### 1. 超时重传

发送方发出数据后等待确认。如果在重传超时（RTO）内确认号没有推进到对应位置，发送方会重传未被确认的数据。

```text
发送方：发送 Seq=200, Len=100
网络：该段丢失
接收方：持续回复 Ack=200 或暂时没有新的确认
发送方：RTO 超时，重传 Seq=200, Len=100
```

RTO 不是固定值。TCP 会参考往返时间（RTT）动态估计；网络抖动时，超时时间通常会变大。

`RTT（Round-Trip Time）` 是一个报文从发送端到接收端、再等确认返回的往返时间。`RTO（Retransmission Timeout）` 是发送方等待确认的重传超时时间。RTO 需要根据测量到的 RTT 和波动情况动态计算，并且通常要大于预计 RTT：

- RTO 过短：网络只是暂时变慢，就可能误判丢包，产生不必要的重传；
- RTO 过长：真正丢包时要等待更久，恢复速度变慢。

### 2. 快速重传

如果接收方连续收到缺口之后的乱序报文，会重复回复相同的确认号。例如 B 丢失后，C、D、E 到达，接收方可能多次发送 `Ack=200`。发送方通常收到 **3 个重复 ACK** 后，就会推断 `Seq=200` 附近可能丢失，提前重传，不必等待 RTO 超时。

“3 个重复 ACK”是常见 TCP 快速重传规则；实际抓包中是否出现、何时出现会受报文数量、接收端行为和系统实现影响。

## 七、SACK 与 D-SACK（了解）

### 1. SACK

`SACK（Selective Acknowledgment，选择确认）` 是 TCP 选项。累计确认只能告诉发送方“连续数据到哪里”，而 SACK 还可以报告已经收到的非连续数据块。例如缺少 `200~299`，但已经收到 `300~399`，SACK 可以携带类似 `300~400` 的已收区间，帮助发送方只重传缺失部分，而不是盲目重传所有后续数据。

SACK 是否可用，需要在握手的 TCP 选项中协商；它不是每个连接都必然启用的 TCP 基础首部字段。

### 2. D-SACK

`D-SACK（Duplicate SACK）` 是 SACK 的扩展，用来报告“某个已经收到过的序列区间又重复到达了”。它能帮助发送方判断重复报文是网络重复、误重传，还是其他异常。D-SACK 不是普通 SACK 的同义词，也不是单独保证可靠传输的重传机制。

## 八、在 Wireshark 中观察

用已有 pcap 或新抓取的 TCP 流，在 Windows Wireshark 中：

1. 找到任意 TCP 报文，右键 **Follow -> TCP Stream**；
2. 使用过滤器 `tcp.stream eq N`，将 `N` 换成实际流编号；
3. 展开 TCP 首部，观察 `Sequence Number`、`Acknowledgment Number`、`Len`、`Flags`；
4. 对照相邻报文：本段 `Seq + Len` 通常对应对端后续的 `Ack`；若含 `SYN` 或 `FIN`，还要额外加 1；
5. 若抓到重传，Wireshark 的 Info 列可能标记 `[TCP Retransmission]` 或 `[TCP Fast Retransmission]`。这只是分析器判断，仍要结合 `Seq`、`Ack` 和时间间隔确认。

## 九、易错点

- `Seq` 编的是**字节**，不是报文数量，也不是 `send()` 次数；
- `Ack=N` 的含义是“下一字节希望为 N”，即已连续收到 `N-1`；
- `Ack` 不能越过乱序缺口；收到更靠后的字节，不等于中间字节已经收到；
- `SYN`、`FIN` 各占一个序列号；普通纯 ACK 一般不占序列号；
- RTT 是测量出的往返时间，RTO 是根据 RTT 和波动估计的重传等待时间，两者不是同一个字段；
- SACK 报告已收到的非连续数据块，D-SACK 报告重复到达的数据块；
- Wireshark 的相对序列号用于阅读方便，不代表 TCP 协议线上只发送小数字。
