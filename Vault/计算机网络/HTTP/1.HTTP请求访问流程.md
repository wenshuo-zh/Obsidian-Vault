# HTTP请求访问流程

## 一、先看整体流程

访问一个 HTTP 链接，可以先记成下面这条主线：

```text
URL
 ↓
解析 URL，得到域名、端口、路径
 ↓
DNS：域名 -> IP
 ↓
TCP 三次握手（HTTP/1.1 常见情况）
 ↓
发送 HTTP 请求
 ↓
接收 HTTP 响应
```

这是一条便于入门的典型流程。实际程序可能命中 DNS 缓存，也可能复用已经建立的 TCP 连接，因此不一定每次都重新查询和握手。

## 二、解析 URL

示例：

```text
http://example.com:8080/docs/a.html?x=1
```

| 部分 | 内容 | 作用 |
| --- | --- | --- |
| 协议 | `http` | 规定使用什么应用层协议 |
| 主机名 | `example.com` | 用于 DNS 查询，找到目标主机的 IP |
| 端口 | `8080` | 找到目标主机上的具体服务 |
| 路径 | `/docs/a.html` | 告诉 Web 服务要访问哪个资源 |
| 查询参数 | `x=1` | 给服务端的额外条件 |

路径不一定对应磁盘上的真实文件，也可能由后端程序动态生成内容。

URL 没写端口时使用默认端口：

```text
HTTP  -> 80
HTTPS -> 443
```

## 三、DNS：域名解析成 IP

网络通信需要 IP 地址。客户端拿到 `example.com` 后，会通过 DNS 查询它对应的 IP：

```text
客户端 -- DNS 查询 --> DNS 服务器
客户端 <-- IP 地址 --- DNS 服务器
```

**DNS 查询不是 HTTP 请求。** 两者的目的和报文格式不同：

- DNS 问：“这个域名对应什么 IP？”
- HTTP 问：“请给我这个主机上的哪个资源？”

DNS 通常使用 UDP 的 `53` 端口，特殊情况下也会使用 TCP 的 `53` 端口。

### DNS 缓存

如果本地缓存命中，客户端可以直接得到 IP；没有命中时，DNS 服务器可能递归查询其他 DNS 服务器，最后返回结果。

```text
本地缓存命中：直接得到 IP

本地缓存未命中：
本地 DNS -> 根 DNS -> 顶级域 DNS -> 权威 DNS
```

初学阶段只需要记住：**DNS 负责把域名转换为 IP，不负责传输 HTTP 正文。**

## 四、端口：找到机器上的服务

IP 只能找到哪台机器，端口才能找到这台机器上的哪个服务。

一台服务器可能同时运行：

```text
IP:80   -> HTTP 服务
IP:443  -> HTTPS 服务
IP:22   -> SSH 服务
```

所以“IP + 端口”才可以更准确地定位网络服务。

端口不是“域名拥有的功能”，而是传输层用来区分服务的编号。客户端连接时也会使用自己的临时端口，形成类似下面的通信端点：

```text
客户端 IP:临时端口  <->  服务端 IP:80
```

## 五、TCP 三次握手

HTTP/1.1 通常运行在 TCP 之上。发送 HTTP 请求前，客户端先和服务端建立 TCP 连接。

```text
第一次：客户端 -- SYN ------> 服务端
        客户端想建立连接，并给出初始序列号

第二次：客户端 <-- SYN + ACK -- 服务端
        服务端确认收到客户端请求，并给出自己的初始序列号

第三次：客户端 -- ACK ------> 服务端
        客户端确认收到服务端回复
```

三次握手的作用：

1. 确认双方的发送和接收能力；
2. 同步双方的初始序列号；
3. 为后续可靠、有序的字节流传输做准备。

注意：TCP 连接建立成功，只表示传输通道建立了，不代表 HTTP 业务一定成功；业务结果还要看 HTTP 响应状态码。

## 六、客户端发送 HTTP 请求

TCP 连接建立后，客户端发送 HTTP 请求。HTTP/1.1 请求通常由四部分组成：

```text
1. 请求行
2. 请求头
3. 空行
4. 请求体（可选）
```

示例：

```http
GET /docs/a.html?x=1 HTTP/1.1
Host: example.com:8080
User-Agent: curl/7.81.0
Accept: text/html

```

### 1. 请求行

```http
GET /docs/a.html?x=1 HTTP/1.1
```

依次表示：

- 请求方法：`GET`；
- 请求目标：路径和查询参数；
- HTTP 版本：`HTTP/1.1`。

### 2. 请求头

请求头是多行 `Key: Value`，用于补充请求信息：

```http
Host: example.com
Accept: application/json
Content-Type: application/json
Content-Length: 15
```

常见字段：

- `Host`：告诉服务端要访问哪个主机，HTTP/1.1 中必须有；
- `Accept`：客户端希望接收的响应媒体类型；
- `Content-Type`：当前请求体的媒体类型；
- `Content-Length`：请求体的实际字节数；
- `Cookie`：客户端携带的 Cookie；
- `Authorization`：身份认证信息。

### 3. 空行

请求头结束后必须有一个空行，用来分隔请求头和请求体。

### 4. 请求体

请求体是可选的，常见于 `POST`、`PUT`、`PATCH`：

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 16

{"name":"alice"}
```

## 七、服务端返回 HTTP 响应

HTTP 响应也通常由四部分组成：

```text
1. 状态行
2. 响应头
3. 空行
4. 响应体（可选）
```

示例：

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 16

<html>...</html>
```

### 1. 状态行

```http
HTTP/1.1 200 OK
```

包含 HTTP 版本、状态码和状态描述。

常见状态码分类：

| 范围 | 含义 | 示例 |
| --- | --- | --- |
| `2xx` | 请求成功 | `200 OK` |
| `3xx` | 重定向 | `301`、`302` |
| `4xx` | 客户端请求有问题 | `400`、`403`、`404` |
| `5xx` | 服务端处理失败 | `500`、`502` |

### 2. 响应头

响应头描述响应的信息：

```http
Content-Type: text/html
Content-Length: 16
Set-Cookie: sid=abc
Location: /login
```

### 3. 空行

响应头结束后有一个空行，后面才是响应体。

### 4. 响应体

响应体可以是 HTML、JSON、图片、音频或视频等数据。`Content-Type` 描述其媒体类型，但不会自动验证正文内容是否真的符合该类型。

## 八、curl 实验

### 实验命令

```bash
curl --http1.1 -v --max-time 15 http://example.com/
```
==参数==
- `--http1.1`：使用 HTTP/1.1；
- `-v`：显示详细过程；`*` 通常表示连接信息，`>` 表示发出的请求，`<` 表示收到的响应；
- `--max-time 15`：最多等待 15 秒；
- `http://example.com/`：目标 URL。

### 实验目的

用 curl 观察下面这条真实链路：

```text
DNS 解析 -> TCP 连接 -> HTTP 请求 -> HTTP 响应
```

不是为了单纯下载网页，而是验证：请求行、请求头、空行、状态行、响应头、响应体在真实输出中的位置。

### 实验结果（Ubuntu，2026-10-03）

关键输出：

```text
* Trying 172.66.147.243:80...
* Connected to example.com (172.66.147.243) port 80
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/7.81.0
> Accept: */*
< HTTP/1.1 200 OK
< Content-Type: text/html; charset=utf-8
< Transfer-Encoding: chunked
< Connection: keep-alive
```

对应关系：

1. `Trying 172.66.147.243:80`：尝试连接 DNS 解析得到的 IP 和 HTTP 默认端口；
2. `Connected ... port 80`：TCP 连接已经建立。三次握手由操作系统网络栈完成，curl 不会逐个打印 SYN、SYN+ACK、ACK；
3. `> GET / HTTP/1.1`：请求行，方法是 `GET`，路径是 `/`；
4. `> Host: example.com`：请求头，说明访问哪个主机；
5. `> Accept: */*`：客户端接受任意媒体类型；
6. `< HTTP/1.1 200 OK`：响应状态行，表示本次请求成功；
7. 一串 `< ...`：响应头；最后的 `<` 后空行表示响应头结束；
8. 后面的 `<!doctype html>...`：响应体，是 HTML 文本。

本次还观察到：

- `Transfer-Encoding: chunked`：响应使用分块传输，没有直接给出 `Content-Length`；
- `Connection: keep-alive`：连接暂时保持，后续可能复用；
- `alt-svc: h3=":443"`：服务器告知未来可以尝试 HTTP/3，但本次命令明确使用 HTTP/1.1；
- `* Mark bundle as not supporting multiuse`：curl 的连接管理提示，不属于 HTTP 响应报文。

## 九、HTTP 和 TCP 的区别

```text
TCP：怎么可靠地传输字节
HTTP：这些字节按什么格式表达请求和响应
```

TCP 负责连接管理、可靠性、顺序和字节流；HTTP 负责请求方法、状态码、请求头、响应头和正文的应用层语义。

因此，HTTP/1.1 通常借助 TCP 传输，但 HTTP 不等于 TCP，也不属于同一层。HTTP/3 使用 QUIC，后续再学习。

## 十、易错点

1. **DNS 查询不是 HTTP 请求**：DNS 和 HTTP 使用不同的协议和报文格式。
2. **端口不属于域名**：IP 找机器，端口找机器上的服务。
3. **路径不一定是真实文件**：后端程序可以动态处理路径。
4. **TCP 连接成功不等于业务成功**：还要检查 HTTP 状态码和响应体。
5. **`send` 和 `recv` 不等于一条完整 HTTP 消息**：TCP 是字节流，后续写 C++ 网络程序时必须处理部分读写和消息边界。
