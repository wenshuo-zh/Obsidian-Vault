# HTTPS 与 TLS 基础

## 一、本次重点

HTTPS 可以入门理解为：

```text
HTTP + TLS + TCP
```

TLS 位于 HTTP 与 TCP 之间，为 HTTP 数据提供：

1. **加密**：第三方难以直接看懂内容；
2. **身份验证**：客户端确认服务器身份；
3. **完整性保护**：发现数据是否被篡改。

本次不深入密码算法数学证明，只理解 TLS 在访问流程中的位置和作用。

## 二、HTTP 为什么不安全

明文 HTTP 数据经过中间网络设备时，可能被窃听或篡改。攻击者还可能冒充目标服务器。

仅有加密也不够：如果客户端和假服务器建立了加密连接，数据仍会交给攻击者。因此 TLS 还必须验证服务器身份。

## 三、TLS 握手的入门过程

简化流程：

```text
1. TCP 三次握手完成
2. 客户端发送支持的 TLS 版本、密码套件等信息
3. 服务端返回选择结果和数字证书
4. 客户端验证证书中的域名、有效期和签发链
5. 双方协商出本次连接使用的会话密钥
6. TLS 握手完成
7. 开始传输加密的 HTTP 请求和响应
```

现代 TLS 通常使用非对称密码完成身份验证和密钥协商，再使用速度更快的对称加密传输大量数据。

## 四、证书证明什么

证书通常包含：

- 服务器域名；
- 公钥；
- 有效期；
- 证书颁发机构的签名。

客户端会检查：

1. 证书是否由受信任机构签发；
2. 当前访问域名是否与证书匹配；
3. 证书是否在有效期内；
4. 证书链是否完整且签名有效。

证书验证通过，只能证明连接的服务器身份符合证书，并不代表网站业务绝对安全。

## 五、加密、身份验证、完整性的区别

| 目标 | 解决的问题 |
| --- | --- |
| 加密 | 防止第三方直接读取数据 |
| 身份验证 | 防止连接到冒充的服务器 |
| 完整性保护 | 防止数据被修改后无法发现 |

这三个目标缺一不可。

## 六、curl 实验

### 1. 观察 HTTPS 访问

```bash
curl --http1.1 -v --max-time 15 https://example.com/
```

重点观察：

- 先连接 `443` 端口；
- TLS 版本和密码套件；
- 服务端证书信息；
- `SSL certificate verify ok` 或对应校验结果；
- TLS 完成后才出现 `GET / HTTP/1.1`。

### 2. 与明文 HTTP 对比

```bash
curl --http1.1 -v --max-time 15 http://example.com/
```

明文 HTTP 通常连接 80 端口，不会出现 TLS 握手和证书验证过程。

### 3. 不安全选项只用于排查

```bash
curl -k -v --max-time 15 https://example.com/
```

`-k` 会跳过证书校验。它可能用于临时排查自签名证书，但不能作为生产环境的正常解决方案，否则会失去服务器身份验证。

## 七、C++ 后端连接

普通 socket 只提供 TCP 字节流，不会自动提供 TLS。C++ 服务端通常使用 OpenSSL 等库，在 socket 之上完成 TLS 握手、证书配置和加密读写。

```text
普通 TCP：send / recv
TLS 连接：SSL_write / SSL_read（底层仍使用 socket）
```

还要处理证书文件权限、私钥保护、握手失败、证书过期和安全配置等问题。

## 八、易错点

1. HTTPS 不是用 TLS 替代 TCP，而是 TLS 通常运行在 TCP 之上。
2. TLS 加密的是应用数据，IP 和端口等网络转发信息仍需要被网络设备看到。
3. 证书主要解决身份验证，不代表网站没有漏洞。
4. `-k` 会跳过证书验证，不能因为“能访问”就长期使用。
5. TLS 握手失败时，可能还没有发送任何 HTTP 请求，因此不会出现 HTTP 状态码。

## 十、学习记录

- 已明确协议层次是 `HTTP → TLS → TCP`，实际建立顺序是 TCP 连接、TLS 握手、HTTP 请求。
- 已理解 TLS 的三个目标：保密性、服务器身份验证、完整性保护；完整性保护表示能够发现篡改，不是保证绝对无法篡改。
- 已完成 `curl --http1.1 -v --max-time 15 https://example.com/` 实验：连接到 443 端口，协商使用 TLS 1.3 和 `TLS_AES_256_GCM_SHA384`。
- curl 输出显示服务器证书的域名与 `example.com` 匹配，并出现 `SSL certificate verify ok`。
- `GET / HTTP/1.1` 出现在 TLS 握手完成之后，验证了 HTTP 报文通过 TLS 传输。

## 十一、手写笔记整理与订正

### 1. 访问顺序

手写总结“在 HTTP 和 TCP 之间加入 TLS，提高安全性”是正确的。更完整的层次和顺序如下：

```text
协议层次：HTTP → TLS → TCP
建立顺序：TCP 三次握手 → TLS 握手 → 加密的 HTTP 请求/响应
```

### 2. TLS 握手展开

```text
1. TCP 三次握手完成
2. ClientHello：客户端发送支持的 TLS 版本、密码套件、随机数和扩展信息
3. ServerHello：服务端选择参数，返回随机数、证书等握手信息
4. 客户端校验证书：域名、有效期、签发链和签名
5. 双方通过密钥协商得到本次连接使用的会话密钥
6. TLS 握手完成
7. 使用会话密钥加密传输 HTTP 报文
```

curl 实验中对应的现象是：先连接 `443` 端口，再看到 TLS handshake、证书信息和 `SSL certificate verify ok`，最后才出现 `GET / HTTP/1.1`。

### 3. 对称加密与非对称密码

- **对称加密**：加密和解密使用同一个会话密钥，速度快，适合加密大量 HTTP 数据。
- **非对称密码**：使用公钥和私钥，计算开销较大，常用于身份验证、数字签名和密钥协商。

“公钥加密、私钥解密”是非对称密码的一种使用方式，但不能简单理解为 TLS 全程都用公钥加密。现代 TLS 1.3 通常使用临时密钥交换协商共享秘密，再使用对称加密传输数据。

### 4. 数字证书与数字签名

数字证书通常包含服务器域名（SAN）、服务器公钥、有效期、签发者等信息。证书中的签名由 CA 使用 CA 私钥生成，客户端使用受信任的 CA 公钥验证。

TLS 握手中，服务器还会使用与证书公钥对应的服务器私钥对握手内容签名，客户端用证书中的公钥验证。这样可以证明服务器持有对应私钥，并发现握手内容是否被篡改。

因此要区分两类签名：

```text
CA 私钥 ──签名证书──> 客户端用 CA 公钥验证
服务器私钥 ──签名握手──> 客户端用服务器公钥验证
```

数字签名用于验证来源和发现篡改，不是让内容绝对无法被修改。

### 5. 本次关键订正

- 手写笔记中的“从证书取服务器公钥，得到 pre-master key”是早期 RSA 握手的简化说法；现代 TLS 1.3 通常通过（EC）DHE 密钥交换协商共享秘密，证书公钥主要用于验证服务器签名。
- `TLS` 名字中虽然有 Transport，但它不是 TCP 那样的传输层协议；在本学习范围内应记为运行在 TCP 之上、HTTP 之下的安全层。
