# HTTP 请求头、响应头、Cookie 与 Session

## 一、本次重点

本次只解决四个基础问题：

1. 请求头和响应头分别有什么作用；
2. 常见头字段表示什么；
3. Cookie 如何保存并携带状态；
4. Session 如何配合 Cookie 保存登录状态。

完成标准：能用自己的话讲清 Cookie 与 Session 的完整交互过程，并能从 curl 输出中找到 `Set-Cookie` 和 `Cookie`。

预计学习时间：约 40～60 分钟。

## 二、请求头和响应头

HTTP 头字段是放在起始行之后、空行之前的附加信息。

```http
GET /users HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer abc123

```

上面是请求头，主要描述客户端身份、希望获取的内容以及请求体格式。

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27
Cache-Control: no-cache
Set-Cookie: session_id=abc123; HttpOnly

```

上面是响应头，主要描述响应正文、缓存策略以及服务器希望客户端保存的信息。

## 三、常见请求头

| 字段 | 作用 |
| --- | --- |
| `Host` | 指定要访问的域名；HTTP/1.1 请求必须携带 |
| `Accept` | 客户端希望接收的响应类型 |
| `Content-Type` | 当前请求体的数据格式 |
| `Content-Length` | 当前请求体的字节数 |
| `Authorization` | 携带身份认证信息，例如 Bearer Token |
| `Cookie` | 携带此前由服务器设置的 Cookie |
| `User-Agent` | 描述客户端程序及版本 |

### Accept 与 Content-Type 的区别

```text
Accept：希望服务器返回什么格式
Content-Type：我现在发送或返回的正文是什么格式
```

例如客户端提交 JSON，同时希望收到 JSON：

```http
Accept: application/json
Content-Type: application/json
```

## 四、常见响应头

| 字段 | 作用 |
| --- | --- |
| `Content-Type` | 响应正文的数据格式 |
| `Content-Length` | 响应正文的字节数 |
| `Set-Cookie` | 要求客户端保存或更新 Cookie |
| `Cache-Control` | 指定缓存策略 |
| `Location` | 指定重定向目标地址 |
| `Server` | 描述服务端软件，生产环境可能隐藏 |

`Content-Length` 必须与实际正文的字节数一致。中文在 UTF-8 中通常占多个字节，不能简单按字符数量计算。

手写笔记中的几个重点可以这样记：

- `Cache-Control`：告诉客户端或中间缓存如何缓存响应；
- `Location`：指定重定向目标地址，常见于 `301`、`302` 等响应；
- `Set-Cookie`：要求客户端保存或更新 Cookie，常用于建立登录状态。

## 五、Cookie 是什么

HTTP 本身是无状态的：两个独立请求默认不知道是否来自同一个用户。

Cookie 是保存在客户端的一小段数据。服务器通过响应头设置 Cookie：

```http
Set-Cookie: session_id=abc123; Path=/; HttpOnly
```

客户端保存后，在符合条件的后续请求中携带：

```http
Cookie: session_id=abc123
```

### 常见 Cookie 属性

| 属性 | 作用 |
| --- | --- |
| `Path` | 限制 Cookie 可以发送到哪些路径 |
| `Domain` | 限制 Cookie 可以发送到哪些域名 |
| `Max-Age` / `Expires` | 指定过期时间 |
| `Secure` | 只通过 HTTPS 发送 |
| `HttpOnly` | 禁止 JavaScript 读取，降低窃取风险 |
| `SameSite` | 限制跨站请求携带 Cookie，降低 CSRF 风险 |

Cookie 不是绝对安全的保险箱，不应直接保存密码等敏感信息。

Cookie 常用于保持登录状态，但客户端保存的是标识，不应该直接保存可信的权限数据。用户可以查看和修改客户端 Cookie，服务端必须重新根据标识查询自己的会话数据。

## 六、Session 是什么

Session 通常是保存在服务端的会话数据，例如：

```text
session_id=abc123 -> 用户 ID 42、已登录、权限信息
```

典型登录过程：

```text
1. 客户端提交用户名和密码
2. 服务端验证成功，创建 Session
3. 服务端生成随机的 `session_id`
4. 响应通过 `Set-Cookie` 把 `session_id` 发给客户端，而不是把整个 Session 数据发出去
5. 客户端保存 Cookie
6. 后续请求通过 Cookie 携带 session_id
7. 服务端根据 session_id 查找 Session，识别当前用户
```

```text
客户端 Cookie：session_id=abc123
服务端 Session：abc123 -> 用户 ID、登录状态、权限信息
```

服务端判断权限时，应以自己保存的 Session 为准，而不是相信客户端传来的 `is_admin=true` 等字段。

### Cookie 与 Session 的区别

| 对比 | Cookie | Session |
| --- | --- | --- |
| 保存位置 | 客户端 | 服务端 |
| 常见内容 | 会话 ID、偏好设置 | 用户身份、权限、会话数据 |
| 容量压力 | 客户端和每次请求 | 服务端内存或存储 |
| 安全重点 | 防止篡改、窃取和跨站携带 | 防止会话 ID 泄漏、固定和过期失效 |

**Session 保存在服务端，但客户端仍需要保存 session_id。** 最常见的做法就是把 session_id 放进 Cookie。

### Cookie 属性的实际含义

| 属性 | 手写笔记中的理解 | 需要注意 |
| --- | --- | --- |
| `Path` | 限制 Cookie 发送到哪些路径 | 例如 `Path=/api` 不代表所有域名都能使用 |
| `Domain` | 限制 Cookie 发送到哪些域名 | 域名范围越大，暴露面越大 |
| `Max-Age` / `Expires` | 设置过期时间 | `Max-Age` 通常按秒数，`Expires` 是具体时间 |
| `Secure` | 只通过 HTTPS 发送 | 不会阻止用户修改 Cookie |
| `HttpOnly` | 禁止 JavaScript 读取 | 浏览器仍可在符合条件时自动发送 |
| `SameSite` | 限制跨站请求携带 Cookie | 可降低 CSRF 风险 |

## 七、curl 实验

### 1. 观察服务器设置 Cookie

```bash
curl --http1.1 -i --max-time 15 \
  "https://httpbin.org/cookies/set?username=alice"
```

重点寻找：

```http
Set-Cookie: username=alice
```

如果响应发生重定向，可先不加 `-L`，观察第一次响应中的 `Set-Cookie` 和 `Location`。

### 2. 保存 Cookie 到文件

```bash
curl --http1.1 -i -L --max-time 15 \
  -c cookies.txt \
  "https://httpbin.org/cookies/set?username=alice"
```

`-c cookies.txt` 表示把服务器设置的 Cookie 保存到文件。

实验结果：第一次响应返回 `302 FOUND`，包含 `Set-Cookie: username=alice; Path=/` 和 `Location: /cookies`；因为使用 `-L`，curl 随后访问 `/cookies` 并得到 `200 OK`。

![[Pasted image 20261005171726.png]]

查看文件：

```bash
cat cookies.txt
```

实验结果：`cookies.txt` 中保存了 `username=alice`，文件采用 curl 的 Netscape Cookie 格式。

![[59b20f09aab42b0b842213e0ca616729.png]]

### 3. 携带已保存的 Cookie

```bash
curl --http1.1 -i --max-time 15 \
  -b cookies.txt \
  https://httpbin.org/cookies
```

`-b cookies.txt` 表示读取文件中的 Cookie 并随请求发送。响应 JSON 中应能看到 `username: alice`。

实验结果：服务端返回 JSON，并识别到 `username: alice`，说明客户端确实携带了 Cookie。

![[Pasted image 20261005171752.png]]

### 4. 直接手动携带 Cookie

```bash
curl --http1.1 -i --max-time 15 \
  -b "username=alice" \
  https://httpbin.org/cookies
```

这相当于让 curl 发送：

```http
Cookie: username=alice
```

## 八、易错点

1. `Set-Cookie` 是响应头，`Cookie` 是请求头。
2. Cookie 保存在客户端，Session 数据通常保存在服务端。
3. Session 并没有让 HTTP 自动变成有状态，而是应用层通过会话 ID 建立请求之间的关联。
4. `HttpOnly` 只是禁止 JavaScript 读取 Cookie，浏览器仍会在符合条件时自动发送。
5. `Secure` 表示只通过 HTTPS 发送，不代表 Cookie 内容已经加密。
6. Token 和 Session 是不同的认证方案，不要把所有身份信息都统称为 Session。
